# GDR-003: セッション間 状態管理の再設計（condition.md の役割見直し）

**Status**: 採用 (Accepted) — 2026-06-30 実装完了
**関連**: GDR-002（condition.md ハンドオフ管理）を handoff 役について置換。

---

## 背景・問題

condition.md が肥大化（149行 / 約44,000字 / ~22-33k トークン、1回 Read の 25k 上限を超過）。更新に時間がかかる割に「役に立っているか不明」「しばしば外す」とユーザーから指摘。

計測した事実:

- **薄く保つべき理由＝品質**（注意予算の希釈／context rot）。コスト・容量ではない。〔公式: Claude Code best-practices / Anthropic context-engineering〕
- **実内容のボトムアップ分類**（実測）:
  - 約50% = DB/SessionStartフックと重複（削除可）
  - 約15% = 開発/インフラ変更ログ（git commit / ADR 行き）
  - 約6% = 方法論・根拠（ADR 行き）
  - 約10% = 次の一手 ／ 約6% = 仮説・確認待ち（→ 外部トラッカー行き）
  - 約7% = 進行中の状態 ／ 約4% = スタンス ／ 約2% = 運用教訓
  - **condition.md 固有で残す価値があるのは約1割のみ**

## これまでの決定

- **スタンス**（その場限りの判断・約4%）→ CLAUDE.md の小セクションに置く（上書き・削除運用。永続化すべきものは knowledge/ADR へ昇格）。
- **重複・変更ログ・方法論・教訓**（約73%）→ 既存の置き場（DuckDB / git / ADR）に書き、condition.md への複製をやめる。
- **「Claude はよく外す」は設計の前提にしない**（洞察として保持。Brier 等で後検証しうる）。
- **トラッカーは GitHub Issues + Projects v2 を採用**（2026-06-30 決定）。状態管理は**ラベルでなく Projects の Status フィールド（単一選択）**で行う。理由: Issue 本来の意味は「問題の起票→解決（open/closed）」であり、ワークフロー状態をラベルで自由に盛るのは器の濫用。状態の排他・優先度・個別の再評価日は Projects のフィールドが素で満たす。（他候補 DuckDB テーブル/in-repo ファイルは GitHub が要件を満たしたため形式採点は省略。）
- **公開を許容**（2026-06-30 決定）。既存の公開リポジトリ `ksyunnnn/Master-Sensei` に**実 Issue** を作り、Project を1つ載せる。別の非公開リポジトリ・下書き Issue は不要。理由: 過去トレードは既に公開済みで、前向きの意図露出も個人小口口座では実害ほぼ無し。実 Issue はフル機能（ラベル・相互参照・通知）が使える。

## 外部トラッカーへの要件

タグ: 〔公〕Anthropic/Claude Code 公式 ／ 〔確〕確立プラクティス（エージェント記憶研究・トラッカー能力モデル）／ 〔推〕私の推測（最小化・明示）

### 必須（満たさない候補は落とす）

- **セッションをまたいで残る。** 開始時に読み、終わりに書く。正本はトラッカー側で、会話ログではない。〔公〕
- **1件ずつ独立したアイテムで持つ。** 固定の ID を振る。長い文章の塊にしない。〔公・確〕
- **状態が移っていく**（未着手 → 対応中 → 完了/取り下げ）。閉じるとき結果を残す（仮説なら「当たり／外れ／判定不能」）。〔公・確〕
- **開始時に読む量は最小・要点だけ。** 開いている分だけ・件数に上限。毎回ぜんぶ読み込まない。〔公〕
- **後から必要な分だけ絞って取り出せる**（状態・優先度・古さなどで）。〔公・確〕
- **1件単位の作成・修正をエージェント自身ができる。** 全部書き直す方式や、人手でしか触れない方式にしない。〔公・確〕
- **コマンド/API で操作できる**（GUI 不要）。ID は意味のあるもの。失敗時は「何を直せばいいか」が分かるメッセージが返る。〔公・確〕

### あると良い（品質を左右する）

- 各アイテムは**「今の状態の短い要約」を上書き更新**しつつ、**変更履歴は消さず残す**（要約と監査の両立）。〔公・確。両立のさせ方は〔推〕〕
- **優先度**と**最後に触った日**を持ち、何から再開するか順番づけできる。〔確〕
- **しばらく放置されたものを表に出す。** 不要になったら「取り下げ」を明示（黙って腐らせない）。先送りもできる。〔確〕
- **他のアイテムや ADR・予測・知見・コミットへの参照リンク**を張れる。〔確〕
- **書く中身のルールがある**（将来の判断に効くものだけ＝やること／生きている仮説／決めたこと／試してダメだった手。雑談は書かない）。最低限の必須項目チェックも。〔公・確。ADR-003 と同じ発想〕
- **任意で期限・再評価日**を持てる（反証期限つきの仮説、カタリストに紐づく次の一手）。〔確〕
- **「進行中の作業」と「確定した知識・ルール」を分ける**。後者は DB/ADR 側に置き、参照だけする。〔確〕

### 使い方として（トラッカーの機能ではない）

- 溜まったストアを**深く読む作業は別エージェントに投げて、要約だけ受け取る**。〔公〕

### 採点に使わない（明示）

- **担当者欄** — 一人なので無意味。
- **意味検索・embedding** — 件数が少なく過剰。ID と絞り込みで足りる。〔推〕

## GitHub 評価（公式ドキュメントベース・推測排除、2026-06-30）

- 必須要件はほぼ全て満たす: 永続/固定ID/`gh issue list --json` で最小読み込み/検索絞り込み/1件単位の create・edit/CLI操作/本文(上書き)＋timeline・comment(消えない履歴)/参照・sub-issue・依存/エクスポート(REST・json)/トークン永続。
- **worktree 競合は解消**: Issue は git リポジトリ内のファイルでなくサーバ側資源。別 worktree 同時稼働でもファイル競合なし。別 issue なら競合ゼロ。同一 issue の同一フィールド同時編集の競合検出は公式に記載なし＝実質後勝ち（対策＝上書きでなく追記コメント）。
- **状態管理**: 素の Issue は open/closed のみ。Status 欄は Projects v2 の機能 → Projects 採用で解決。`gh project item-list --query "-status:Done" --format json` で読みは軽い。書き込み(`gh project item-edit`)は item-id/field-id/project-id/option-id が要るが、project/field/option-id は固定でキャッシュ可。トークンに `project` スコープが必要（`gh auth refresh -s project`、保有未確認）。
- 耐久性/バックアップ: REST `GET …/issues` や `--json` で全件エクスポート可＝囲い込み小。

## 実装結果（2026-06-30）

- **GitHub Project #2** 作成（https://github.com/users/ksyunnnn/projects/2）。実 Issue を `ksyunnnn/Master-Sensei` に作り Project に載せる。
- フィールド（**ASCII名・値は日本語**）: `state`(未着手/対応中/完了/取り下げ) `kind`(次の一手/仮説) `result`(当たり/外れ/判定不能) `review`(日付)。ID は `docs/worktracker.md` にキャッシュ。
- **設計補正（実装中の判断）**:
  - フィールド名を ASCII に。理由: jq で日本語**キー**を参照すると encoding 不整合で null。値は日本語のまま。
  - 「完了/取り下げ」は **Issue を close** して表現（Issue 本来の意味に合致）。開始時の読み取りは `--query "is:open"` で堅牢化（日本語値での filter を避ける）。
  - 優先度フィールドは陳腐化のため不採用（緊急度は `review` 日付＋件数で捌く）。「先送り」も Status 値でなく `review` 未来日付で表現。
- **移行実施**: ① Stop フック（`session_stop_check.py`）から condition.md 鮮度判定を撤去 ② CLAUDE.md に「作業トラッカー」節・「スタンス」節を追加、Structure 表/終了前手順/ルーティングを更新 ③ condition.md 冒頭に非推奨バナー（履歴として保持・更新しない）④ `docs/worktracker.md`（運用手順・IDキャッシュ）新設。
- **seed**: 積み残しを Issue #7（進行中状態の置き場）・#8（SessionStart 注入検討）として起票し、トラッカーで管理開始（ドッグフーディング）。

## 残課題（トラッカーで管理）

- 進行中状態（約7%）の最終置き場 → **Issue #7 → 2026-07-01 決着（下記）**。
- SessionStart フックへの未完了サマリ注入 → **Issue #8 → 2026-07-01 見送り（not planned）**。gh 呼び出し ~1.3s で毎セッション起動が 0.5s→1.8s に増える一方、既に「開始時に手動 read」ルールが存在し上乗せ価値は読み忘れ防止のみ。キャッシュも低頻度セッションでは無効。手動 read（現行ルール）を正とした。

## Issue #7 決着（2026-07-01）: 「進行中状態」約7% に新しい置き場は作らない

分析の結果、「進行中状態」約7% は単一カテゴリではなく2種に分解でき、それぞれ**既存の置き場**で足りると判断した（極小ファイル新設は不採用）:

| 中身 | 置き場 | 鮮度担保トリガー |
|---|---|---|
| (a) 保有ポジションの**事実**（銘柄・数量） | 判断層 `trades`（filled/exit_date、判断時キャッシュ）。SoT は Saxo 実約定（`account_transactions` / Saxo API） | **日次ワークフローの `/sync-saxo`**（毎セッション Saxo から引き直す。ADR-012 step 5、2026-07-01 追加） |
| (a) 監視の**戦術ナラティブ**（例: $249 押し目監視） | CLAUDE.md スタンス節（揮発的・上書き運用） | セッション終了時の Claude 上書き（Stop hook 運用） |
| (b) 進行中の**調査・確認作業**（WIP） | 作業トラッカー `state=対応中` | worktracker.md「進める」コマンド＋起票ルール |

**Issue status（Project state=対応中）で保有監視を持つ案を却下した理由**: (1) 二重管理＝保有は既に trades/Saxo が SoT で持つ（worktracker.md「入れないもの＝trades」に反する）、(2) 陳腐化＝監視パラメータはザラ場中に動くが Issue はセッション粒度（優先度フィールドを廃止したのと同じ理由）、(3) ライフサイクル不一致＝ポジションの決済は trades の status 遷移で表現され Issue close と二重。ただし WIP（b）については state=対応中 が正しい置き場。

**トリガーの穴の解消**: 決着時点で (a) の鮮度担保が「DBがずれてる気がする→/sync-saxo」オンデマンドのみで、毎セッション引き直す運用が未 codify だった。日次ワークフロー（ADR-012）に `/sync-saxo` を step 5 として追加し、決定が乗るトリガーを実在させた。
